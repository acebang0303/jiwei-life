# 秒杀压测基准报告

> 运行方式见 `run_load.sh`。前置：后端运行、`gen_tokens.sh` 生成 tokens.csv、重置活动库存。
> 原始数据归档：`reports/*.jtl`（逐请求明细）、`reports/*-statistics.json`（JMeter 聚合），可复核本报告全部数字。

## 测试方法学说明

### 这是哪种压测

**瞬时并发脉冲 + 数据正确性验证**，针对秒杀开场瞬间的场景：

- JMeter 真实线程并发（非脚本模拟），每线程一个独立用户 token（CSV 参数化），一人一单
- 传播链路：`限流切面 → 活动元数据三级缓存 → RocketMQ 事务消息（本地事务执行 Lua 预扣）→ 消费端建单`
- 业务正确性校验：**三方一致性**（Redis 库存 / DB 库存 / 订单表）+ 零超卖 + 超时回补终态闭环
- 分位数口径：逐请求 `elapsed` 列（完整响应时间），最近秩法；JMeter summary 的 Avg/Min/Max 同源

### 与「企业级容量/验收压测」的差距（诚实对照）

| 维度 | 本测试 | 企业级标准 |
| --- | --- | --- |
| 加压方式 | 固定并发单轮 2s 脉冲 | 阶梯加压（多档并发）找拐点与最大吞吐 |
| 持续时间 | 秒级瞬时 | 目标 TPS 持续 10–30min（验内存泄漏/连接池/GC/慢 SQL）|
| 环境 | JMeter/后端/中间件同一台机器（Docker Desktop）| 独立压测机 + 类生产环境 |
| 样本量 | 500–1000 请求/轮 | 单场景万级请求（p99.9 才有统计意义） |
| 监控 | 系统 CPU 采样 + 应用日志 | APM：GC、连接池水位、慢 SQL、MQ 堆积 |
| 验收口径 | 探索性测量 | 先定 SLA（如 P99<500ms、错误率<0.1%）再对照 |

**定性**：这是「并发稳定性与数据正确性验证」，能回答"会不会超卖、会不会错单、瞬时并发扛不扛得住"；
**不能**回答"系统最大吞吐是多少、跑 1 小时稳不稳、生产环境容量多少"。对外描述请勿使用"企业级压测"一词。

秒杀场景说明：库存是有限资源，多轮循环第 2 轮起全部售罄，测不到有效事务，故业界秒杀压测普遍采用
"清空重置 + 单轮脉冲 + 反复多轮"的方式，本报告即是该方法。持续负载验证应另行设计（如无限库存活动）。

### 环境（记录 #2/#3 一致；记录 #1 为限流 200 的旧版本）

- 后端：jiwei-modules，localhost:8080，JDK 21 虚拟线程，MySQL 连接池 20
- 中间件：Docker（MySQL 8 / Redis 7 / RocketMQ 5.3.0）与后端同机
- JMeter：apache-jmeter-5.6.3（headless，`-n`），与后端同机
- 活动：id=11（dish_id=1，限购 1/人）；每轮压测前重置：DB `stock=N, sold=0` + Redis `SET seckill:stock:11:1 N` + `DEL seckill:users:11`
- 每轮用户：全新用户（openid 带时间戳随机），避免撞 `uk_user_activity` 唯一索引

## 基准记录 #2 — 500 并发（2026-10-12 17:57，热路径优化后）

> **勘误（2026-10-12 晚复核）**：本轮活动为 **id=11**（dish_id=1），原文"id=7"系笔误。
> 原始数据已归档 `reports/v2-20261012-1757.jtl` 并复核：URL=/user/seckill/11/buy，与下文数字一致。

### 优化内容
- 活动元数据三级缓存（Caffeine 5s → Redis 300s+抖动 → DB），`seckillBuy` 热路径 0 次 DB 查询

吞吐 226/s：瓶颈在事务消息同步等待半消息确认（强一致设计取舍）。

## 结论

1. **正确性（三轮复现，稳定达标）**：500/1000 并发下零超卖、零系统错误；Redis 库存、DB 库存、订单数
   三方严格一致；压测后 15 分钟超时回补闭环后三方回到初始值；对账任务零修复。
2. **性能（热态 1000 并发）**：p50 40ms / p99 328ms / Err 0；峰值吞吐窗口 413.6/s（受本机单机环境限制，
   非生产容量）。
3. **限流保护**：阈值 2000 QPS，本轮两轮并发量均未触发（是"保护未发生介入"，非"保护失效"）；
   限流生效行为见记录 #1（阈值 200 时代 228 拒绝）与单元/集成测试。Redis 故障降级本地桶见
   `RateLimitAspect`。若需复现限流拒绝，临时调低 `@RateLimit.permitsPerSecond` 即可。
4. **测试边界**：本报告是瞬时突发 + 正确性验证，不是容量评估；阶梯/长稳/混合场景未覆盖（见方法学对照表）。

## 数字引用建议（对外沟通口径）

推荐（热态、可复现）：

> 秒杀链路本地压测：1000 并发瞬时抢购，零超卖、零错误，1000 单 100% 建单，Redis/DB/订单三方严格一致，
> 热态 P50 40ms / P99 328ms；另有冷启动 500 并发场景 P50 109ms 对照。

**不建议继续引用**：
- 记录 #1 的「p50 36ms」：被限流 fast-fail 拉低，非成交延迟，且当前限流阈值已变
- 「228 请求被限流拦截」作为性能亮点：那是 200 QPS 阈值下的保护性截断，现阈值 2000 下不会出现；
  要讲就讲"限流+熔断保护机制及其验证"，不要把截断数当吞吐成绩
- 「企业级压测」表述：见方法学对照表，本项目环境达不到该标准，讲"并发稳定性验证"更稳妥
